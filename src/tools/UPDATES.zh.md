# 软件包与源码更新

[English](UPDATES.md)

`packages` 在应用前显示计划。`locachy-pkg plan` 和
`locachy-pkg apply [TARGET...]` 就是该界面使用的后台。检查不会安装软件源的包，
也不会在宿主执行下载的配方。

## 先源码，再更新与之匹配的宿主

选中 LOCachy 的源码更新时，应用先安装该源码及其包管理工具。新的更新程序
重新检查后，才更改宿主软件包或重建容器。因此配方和合约来自同一份已安装源码，
不再是旧配方配新测试。只应用宿主时，保留已安装源码及其测试。

源码已安装但构建失败时，仍保留“未构建”标记。之后检查必须继续提供程序重建；
仅宿主包版本相同，不代表新程序已经构建。包管理工具安装或软件包声明失败时，
应用会先重试这份源码的准备步骤，再规划宿主。第二阶段保持在所选源码上；最后
检查发现的新提交留给下一份计划，不在更新途中悄悄安装。

`/usr/local/lib/locachy/source-commit` 记录已应用的源码，即整个更新都已完成的
提交。获取某个提交，或应用把它的源码树放到位，都不改变它。在计划里不再剩下
该更新的任何部分之前（其本地包已构建、声明的包已安装、程序已构建），该提交
记在 `/usr/local/lib/locachy/source-pending` 中，计划附一条同时写明两者的说明。
因此中途停下的更新（例如某次构建在等待源码签名密钥）仍以之前的提交为已应用；
完成它的那次应用才记录新提交。`packages` 及 `settings` 的“关于”页显示已应用的
提交，`packages` 也显示待完成的提交。获取到的提交就是已应用的提交且没有待完成
的部分时，检查不提供源码更新：安装只把该提交的一部分放进
`/usr/local/src/locachy`，并把所选模块加进其中的 packages 和 rc.conf，因此不拿
源码树与它比较。

`declare-packages` 记录基础及可选模块的软件包定义。源码为已启用模块新增的包
自动进入 `/etc/locachy/packages`；明确删除的包不会重新加入。没有记录时，
以随源码附带的 08d2a66 定义为起点，不假定所有可选模块均已启用。这里以模块
首个包是否已声明判断启用状态。该脚本只声明，不安装。

已声明但缺失的软件源包，与宿主事务一起固定，并装进各候选包的一次性构建、
测试根及宿主最终事务。不能再靠手工补一个新库才能让新测试编译。
AUR 及本地构建仍有各自独立、明确的失败路径。

## AUR 源签名密钥

AUR 包在宿主的 pacman 事务之后才构建。Apply 在改动应用预设、软件源数据库或
软件包之前，先用 `locachy-build --check-keys` 查看这些构建将核对的源签名密钥。
若同一次 Apply 还要安装 LOCachy 的源提交，该源照常先安装，再由更新后的更新程序
在改动任何宿主目标之前查看密钥；此时的拒绝会保留已安装的源，其他一概不改。该命令读取各配方在 AUR 上的 `validpgpkeys`，并只在构建用户的
密钥环中查找这些密钥。它不构建任何东西，也不获取、导入或信任任何密钥。只要有一个
密钥尚未被信任，整次 Apply 即以状态 3 拒绝（任务的 `keys` 状态）。对每个密钥，它会
显示：包名、指纹、声明该密钥的配方（及其 `.SRCINFO` 链接）、配方中的签名源，以及
用来核对的上游项目。它还会显示 root 在核对之后要执行的命令：
`locachy-build --trust-key 指纹`。由于什么都没有改动，密钥信任之后直接重新 Apply
即可。这种拒绝报告为"事务前拒绝"（refused before any change），绝不写成
"not done"。"not done" 只表示某个目标已经开始执行后失败。只有人能添加密钥，没有任何
选项或变量能跳过这次查看。构建本身遇到未信任的密钥时仍会停下，作为第二道防线。

## 应用预设

应用预设来自单独的仓库（`apps_repo`、`apps_branch`），不来自源码。检查把其目录的提交固定为
`apps` 目标；应用在源码之后、宿主之前安装它，合并跟随预设的配置，从不为此构建或安装软件包。
这一步失败不阻止其他部分。见 [APPS.zh.md](APPS.zh.md)。

## 软件源分层

LOCachy 把软件源当作一组分层来读，优化程度最高的在最前：本 CPU 及其以下各级的
CachyOS 构建，然后 ALHP，然后 `[cachyos]`，最后 Arch（顺序由 `locachy-repos`
写定）。对某个软件包，无论它在哪一层，都取版本最新者；只有版本完全相同时，才取
更高（更优化）的一层。同一发布版的重新构建带有更高的 `pkgrel` 后缀（`3.6.5-1.1`
比 `3.6.5-1` 新），因此已重新构建某发布版的那一层，胜过其下的旧构建。

pacman 自身只从第一个含有该软件包的软件源取包，不管那个构建多旧。尚未重新构建新
发布版的那一层，会把旧版本及其链接的 soname 摆在更新的下层构建之前。优化过的
openssl 以及基于它构建的 tor 因此可能被压住，而 Arch 较新的 openssl 却被提供，更新
就会出错。

`locachy_stack.py` 实现这一规则，用于：

- 检查与计划。`checkupdates` 把数据库整份取回到 `/var/lib/locachy/checkupdates`，取回
  前先把它们的时间设为纪元。pacman 的刷新会保留比镜像副本新的数据库，并从它所请求的镜像
  取签名。某个镜像停滞而故障切换到较旧的镜像时，旧镜像的签名会去校验被保留的数据库，检查便
  会失败，直到出现更新的副本。分层视图位于 `/var/lib/locachy/checkupdates/merged`。更新
  列表、显示的信息及搜索都读这个视图。ALHP 的镜像主要按速度排序（见下文"镜像排序"），
  因此较旧的镜像仍可能提供数据库，更新随之使用该镜像的数据。
- 宿主应用。合并后的数据库在 pacman 自己的锁下替换 `/var/lib/pacman/sync`，并记录
  在 `/var/lib/locachy/sync-published.json`，随后对它们运行 `pacman -Su`。LOCachy
  从不运行 `pacman -Syu`：原始刷新会把软件包从分层中拿出来。
- 全新根（`make-root.sh`）。数据库另行取回并合并进新系统，新系统把它们记为已发布
  的数据库，然后用 `pacman -S` 安装。
- `locachy-repos` 在启用或停用某个分区前的软件源检查。

合并后的数据库经过改写，本身不带签名。其中的软件包仍逐个验证签名：`SigLevel` 为
`Required DatabaseOptional`，接受未签名的数据库，而每个软件包都保留自己的签名。

改写后的数据库时间设为纪元时间（0）。pacman 刷新时，只有镜像上的副本比本地文件新，
才会下载数据库，但本地缺少的签名仍会取回。若按合并时刻标时间，改写后的数据库可能
比镜像上的新：pacman 保留它，却配上镜像的签名，两者永远对不上，每次刷新都会失败。
时间为 0 时，普通的 `pacman -Sy` 会连同签名把它完整重新下载，下面的 guard 随后便能
发现它已被替换。

`locachy-pacman-guard` 会拒绝手动输入的 pacman 事务，前提是宿主的数据库已不再是
LOCachy 发布的那一份（例如手动执行过 `pacman -Sy`），且不做任何改动。运行
`locachy-pkg plan`，再运行 `locachy-pkg apply host`，即可重新发布分层。自记录引入
以来还没有过 LOCachy 更新的系统尚无记录，因此在首次更新写入记录之前，不会因此原因
被拒绝。

## 镜像排序

`locachy-repos rank` 从本机为 `/etc/pacman.d` 中的镜像列表排序：Arch 的用 reflector，
CachyOS 和 ALHP 的用 rate-mirrors。它作为系统任务运行，经过已开启的网络层。某个列表只有
在排序得到镜像时才会被替换。若列表是之前的排序写入的，而这次排序得到的镜像不到它的一半，列表
也保持不变：曾有一轮测速中大部分镜像超时，把 CachyOS 的列表从 16 个镜像缩成了 1 个。此时任务
日志会说明这一点，这次排序仍算完整排序。软件包自带的列表，只要排序得到镜像就会被替换。在设置的"软件源"中，"镜像"一行按 Enter 即手动排序。这一行
也显示上次完整排序的时间。完整排序指每个列表都得到了镜像的那一次，记录在
`/etc/pacman.d/.locachy-ranked`。

列表收录哪些镜像：CachyOS 的镜像 API 列出每个 CachyOS 镜像的健康状态和同步延迟。凡是它列为
https、健康、未过期且落后不超过 10000 秒（cachyos-rate-mirrors 使用的 RATE_MIRRORS_MAX_DELAY）
的镜像都会测速，列表收录其中每个有响应的镜像（2026-11-11 有 27 个这样的镜像）。rate-mirrors 自带
的 cachyos 模式只测本机附近每个国家的两个镜像，所以它给出的列表只有它碰巧测到的那几个：一次测试
得到 16 个，几分钟后只有 1 个。API 没有响应时，测速的是当前列表里的镜像。ALHP 的列表收录每个
有响应的已知 ALHP 镜像。

ALHP 和 CachyOS 的顺序遵循用户的规则。规则只决定顺序，每个有响应的镜像都保留：

- 基本顺序按速度，最快的在前。
- 速度不低于最快镜像一半的镜像中，数据最新的在前。ALHP 的日期取所测数据库的 Last-Modified，用只取
  一个字节的 GET 读取（有的镜像会重定向到不接受 HEAD 的存储）。CachyOS 的日期用其 API 报告的同步
  延迟，因此不增加请求。
  有已知日期的镜像排在没有日期的前面；日期相同或都没有日期时，较快的在前。所以最快的镜像
  不一定排第一：数据比它新的镜像，或在它没有日期时有日期的镜像，会排在它前面。
- 其余镜像按速度排列。

镜像还会定期重新排序：

- 由谁运行。进程 1 启动服务 `service_repos_rank`（`locachy-repos rank-timer`）。它一直
  睡到下一次排序到期，然后提交固定的系统任务 `repos-rank-due`（`locachy-repos rank --due`）
  并等它结束。任务在排序之前会再判断一次是否到期。
- 间隔。间隔是 rc.conf 的 `repos_rank_days`，单位为天，允许小数：`0.5` 表示每 12 小时。
  安装时会把 `repos_rank_days="1"`（每天一次）写进 rc.conf，每次更新也会在缺少时补上。
  0 或更小表示只手动；不是数字的值按 1 处理；大于 3650 的按 3650 处理。在设置中它对应
  "软件源"下的"自动重新排序镜像"一行，可选只手动，或每 1、2、3、5、7、14 天。这一行也
  显示下一次排序的时间，即 `locachy-repos status` 的 `next` 行：本地时间、`now` 或 `off`。
- 何时到期。间隔从上次完整排序算起，不论是谁做的，所以手动排序会把下一次推后。没有记录，
  或上次排序留下了没有镜像的列表时，立即到期。
- 失败。排序失败后一小时再试，不会更早。失败包括任务失败或被取消，以及排序留下了没有
  镜像的列表。
- 修改。服务每次醒来都重新读取 rc.conf 和记录。两者任一改变时（通过对 `/etc/locachy`
  和 `/etc/pacman.d` 的 inotify），以及最迟每天一次，它都会醒来。因此改间隔不需要重启。
  它的定时器按墙上时钟（`CLOCK_REALTIME`）计时，所以在睡眠或休眠期间到期的排序会在唤醒后
  运行。
- 关闭。设置 `repos_rank_days="0"`，或在设置中选择"只手动"。服务继续运行，但不再排序。
  不要靠删除 `service_repos_rank` 一行来关闭排序：下次更新会把它写回去。

## 软件包合约

本地补丁包在一次性根中以非特权用户构建，使用固定的软件源快照。精确封存的
产物一同装进另一个一次性根，可信合约在其中执行，不暴露宿主显示或输入设备。
证据记录完整产物集合、目标包、源码哈希及必需合约编号。不一致则停止宿主更新，
不能以编译器成功退出来绕过。

同一快照下，之前一次尝试留下的结果，只要上述各项校验仍然成立（宿主、配方、目标包集合、
可信测试源和产物哈希都与本次快照一致，且是一起测试的），就直接沿用、不再编译。因此同一计划的
重试不编译任何东西；这些输入一旦变化，就重新编译。

`tools/test-local-packages.py`、`test-update-transaction.py` 及
`test-prepared-builder.py` 用替身检查流程，不证明新的一组真实软件包已通过合约。

## 添加包名

宿主的添加输入框接受空格分隔的多个包名，每个作为独立参数传递。后台先验证
整批请求，依次查询本地配方、软件源及 AUR，再更改清单。未知包名和查询失败
均不更改清单。既有的多名同一行按独立包读取；删除一个保留其他名字。

添加、删除声明仍会运行系统对账，而不只是单包 pacman 命令。
失败输出保存在其系统任务的日志 `/run/locachy/jobs/ID.log` 中（home 列出各任务，见 [JOBS.zh.md](JOBS.zh.md)）；prepared 更新失败时，计划及合约日志
保留在 `/var/lib/locachy/local-packages/transactions/` 下。不能为了越过错误而删除
这些日志或跳过合约。
